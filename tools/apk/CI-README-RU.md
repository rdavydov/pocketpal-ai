# APK и автоматические релизы на GitHub

GitHub собирает **PocketPal AI Community** на Ubuntu без зависимостей с вашего компьютера. Windows-команда [build-apk.cmd](../../build-apk.cmd) остаётся доступной; её окружение описано в [README-RU.md](README-RU.md).

Готовый файл — `pocketpal-ai-community-<версия>-android7.apk`: один самостоятельный `prodRelease` APK для `arm64-v8a` и `x86_64`, пакет `io.github.rdavydov.pocketpalai`. Минимум — Android 7.0/API24 по манифесту. Модели LLM и речи не включены. Применяется штатный `PLUS_STORE_GATE=false`; серверные покупки PalsHub этим флагом не открываются.

## Получить APK вручную

1. Откройте [Actions репозитория](https://github.com/rdavydov/pocketpal-ai/actions).
2. Выберите **Community auto release** → **Run workflow**, нужную ветку и режим **build**. Это режим по умолчанию: он не создаёт релиз и не меняет `main`.
3. Дождитесь успешных проверок, сборки и Android smoke-теста.
4. Внизу страницы запуска, в **Artifacts**, скачайте `community-apk`. GitHub выдаёт ZIP: распакуйте его и устанавливайте находящийся внутри `.apk`, а не ZIP.

Для этой сборки секрет публикации не требуется. Отдельный workflow **Community APK** также можно запустить вручную для выбранной ветки; он использует ту же сборку и проверку.

Actions-артефакт с APK хранится **1 день**, диагностические артефакты сборки и smoke-теста — **7 дней**. Скачивание Actions-артефактов обычно требует входа в GitHub. Для постоянной публичной ссылки используйте [GitHub Releases](https://github.com/rdavydov/pocketpal-ai/releases): там APK прикрепляется отдельным файлом и доступен без входа, пока релиз не удалён владельцем.

## Автоматический выпуск новой версии

**Community auto release** проверяет стабильные [релизы оригинального PocketPal](https://github.com/a-ghorbani/pocketpal-ai/releases) каждый час, на 17-й минуте UTC. Это опрос GitHub API: время фактического запуска может сдвигаться из-за очереди GitHub.

Последовательность:

1. Найти более новый стабильный upstream-релиз и зафиксировать точный коммит его тега. Версии, не превышающие уже опубликованную Community, пропускаются; существующий `community-v1.23.0` не заменяется.
2. Подготовить обновление отдельно от удалённого `main`. Сохранить пакет, имя, ключ, сборочную обвязку и workflows форка. Неизвестный конфликт прекращает выпуск вместо выбора произвольной стороны merge.
3. Выполнить lint, проверку типов, тесты, native-сборку и проверки готового APK.
4. Установить **этот же APK** в эмулятор API35/x86_64, пройти onboarding, дождаться интерфейса чата и сохранить настоящий скриншот и журнал.
5. Только после успеха проверить, что исходный `main` не изменился, и отправить проверенный коммит и тег `community-v<версия>`.
6. Подготовить draft Release, прикрепить APK, отчёты и свежий скриншот, проверить загрузку и опубликовать релиз с описанием изменений, исходниками, требованиями и сведениями о подписи.

Одновременно выполняется одна цепочка выпуска. Если загрузка или публикация оборвалась, повторный запуск продолжает незавершённый выпуск того же тега. Опубликованные файлы автоматически не перезаписываются. Конфликт merge, неверная версия, изменение `main` во время сборки или ошибка тестов требуют исправления причины; последний опубликованный релиз остаётся доступным.

Ручные режимы **Community auto release**:

| Режим     | Поведение                                                                                                                                                      |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`   | Собрать выбранную ветку и выдать Actions-артефакт; без публикации и изменения `main`.                                                                          |
| `check`   | Проверить upstream сейчас; при новой версии выполнить полный автоматический выпуск. Для публикации выбирать ветку `main`.                                      |
| `preview` | Подготовить найденное обновление, собрать и проверить его; не отправлять изменения и не публиковать релиз. Если обновлений нет, тяжёлая сборка не запускается. |

## Доступ для публикации: PAT или GitHub App

Настройте **один** из двух вариантов самостоятельно через GitHub. В репозитории Actions уже активны. Секреты добавляются в **Settings → Secrets and variables → Actions**. Не отправляйте токены и приватные ключи в чат и не коммитьте их в файлы.

Приоритет имеет Secret **`COMMUNITY_RELEASE_TOKEN`**. Если он задан, publisher использует PAT; значения GitHub App не требуются. Если этого Secret нет, publisher использует App. Учётные данные нужны только финальному этапу публикации после проверок; сборочные jobs не получают их.

### Вариант 1: fine-grained PAT

1. В настройках аккаунта откройте **Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**.
2. Выберите владельца `rdavydov`, **Only select repositories** и только `pocketpal-ai`.
3. В **Repository permissions** задайте **Contents: Read and write** и **Workflows: Read and write**. `Metadata` предоставляется GitHub автоматически; дополнительные права аккаунта не нужны.
4. Установите ограниченный срок действия, например **90 дней**, если это допускают настройки аккаунта. Запишите дату: по истечении токен нужно заменить. Правила GitHub или владельца могут ограничивать доступные сроки.
5. Создайте repository Secret **`COMMUNITY_RELEASE_TOKEN`** и вставьте значение токена.

Этот PAT предназначен для GitHub API и отправки исходников; он не является Android-ключом подписи. Если PAT истёк или его права неверны, замените Secret и повторите неуспешный запуск. Для перехода на App удалите `COMMUNITY_RELEASE_TOKEN`, иначе PAT продолжит иметь приоритет.

### Вариант 2: GitHub App

1. В **Developer settings → GitHub Apps** создайте App для собственного аккаунта. Можно отключить webhook: контроллер работает по расписанию и ручному запуску.
2. Разрешите App только **Contents: Read and write** и **Workflows: Read and write**. Установите её только на `rdavydov/pocketpal-ai`, не на все репозитории.
3. Скопируйте **Client ID** в repository Variable **`COMMUNITY_APP_CLIENT_ID`**.
4. Сгенерируйте приватный PEM-ключ App и добавьте его целиком в repository Secret **`COMMUNITY_APP_PRIVATE_KEY`**. Храните резервную копию ключа у себя; значение не должно появляться в исходниках или логах.
5. Убедитесь, что Secret `COMMUNITY_RELEASE_TOKEN` отсутствует, если хотите использовать App.

Publisher создаёт короткоживущий installation token после длительной сборки. Обычный `GITHUB_TOKEN` не заменяет выбранные учётные данные для полноценного обновления workflow-файлов. Подробнее: [права GitHub App для Git](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#choosing-permissions-for-git-access).

Сейчас `main` не защищена обязательным PR. Если позже включите ruleset или защиту ветки, разрешите выбранному боту подходящий доступ к обновлению `main` либо автоматическая отправка будет остановлена GitHub. Workflow не обходит настройки владельца силовой перезаписью истории.

## Подпись и проверяемые возможности

CI сохраняет **общедоступный тестовый ключ** `android/app/debug.keystore`, alias `androiddebugkey`, `CN=Android Debug`, RSA 2048. Новый ключ на каждом запуске не генерируется. Это позволяет обновлять опубликованную Community 1.23.0 с тем же пакетом и сертификатом. PAT и ключ App управляют доступом к GitHub, а не подписью APK.

Проверяются версия исходников/манифеста, имя и пакет, обе ABI, отсутствие `debuggable`, сертификат, native payload, Plus gate OFF и выравнивание ZIP/ELF 16 KB. Общий инструмент метаданных и верификации используется Windows-обвязкой и Linux-сборкой.

Smoke-тест подтверждает установку и загрузку настоящего React Native UI в эмуляторе. Он **не проверяет** локальную генерацию LLM, полный голосовой разговор, физический Android 7, GPU/NPU, Google Sign-In или серверные операции PalsHub. Наличие minSdk24 не является результатом запуска на Android 7.

Первый холодный запуск новой сборочной цепочки на GitHub должен проверяться отдельно. Предыдущая успешная Windows-сборка и локальные unit-тесты не объявляются доказательством успешной серверной сборки. В частности, POSIX-сценарии тестов требуют Ubuntu; их результат нельзя подменять результатом запуска в Windows.

## Если запуск завершился ошибкой

- Откройте красный job и первый неуспешный шаг. Для native-сборки скачайте `community-build-failure-<run>-<attempt>`, если он создан; для устройства — `community-apk-smoke` с `checks.json`, `app.log`, `ui.xml` и `smoke.png`.
- При отсутствии обновлений `prepare` сообщает `no-update`, а последующие тяжёлые jobs пропускаются — это нормальный результат.
- При отсутствии доступа проверьте срок и права PAT либо Client ID, PEM-ключ и установку App. Не добавляйте production Firebase/Play/iOS-ключи оригинального проекта: Community-процесс их не требует.
- После исправления причины используйте **Re-run failed jobs**. Если промежуточный APK или кандидат уже истёк, запустите workflow заново, чтобы восстановить тот же незавершённый тег или подготовить обновление снова.
- Чтобы остановить автоматику, откройте workflow **Community auto release** и выберите **Disable workflow**. Это не удаляет опубликованные APK.

GitHub может [отключать расписания публичных репозиториев после 60 дней без активности](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows). При необходимости включите workflow снова через **Enable workflow**. Не полагайтесь на расписание как на гарантию мгновенного обнаружения релиза; ручной `check` доступен отдельно.
